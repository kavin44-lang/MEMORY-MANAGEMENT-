Abstract 
This report presents the concept, design and expected operation of a Product Management System 
developed using Java Swing, JDBC and MySQL. The purpose of the system is to organise product 
information in a structured database instead of relying on paper records or separate spreadsheets. 
A typical product record contains a unique product identifier, name, category, price, quantity and other 
useful details. The desktop interface provides a convenient way to enter and view this information. 
Java code performs validation and coordinates user requests, JDBC communicates with the database, 
and MySQL stores the records permanently. 
The report discusses the motivation, problems with manual inventory records, functional requirements, 
layered architecture, data safety, possible implementation challenges and a testing plan. The project is 
described as a design where the exact implementation cannot be verified from source code. Sample 
outputs are illustrations, not evidence of completed tests. 
Keywords: Product Management System, Java Swing, JDBC, MySQL, CRUD, inventory, database 
connectivity, input validation.

1. Introduction 
1.1 Background 
Products are the central records in shops, stockrooms and small organisations. Each product needs an 
accurate name, identifier, selling price, category and available quantity. When these values are stored 
in different notebooks or files, the information becomes difficult to maintain. A central application 
reduces repeated work and helps users retrieve the latest record. 
Product management software provides a structured way to maintain information. It is especially 
useful when products are frequently added, prices change or stock quantities need to be corrected. 
1.2 Motivation 
The motivation for this project is to make basic product record management simple and dependable. A 
desktop application with clear forms and a relational database is a practical exercise in connecting a 
graphical user interface with persistent storage. 
1.3 What is a Product Management System? 
A Product Management System is an application used to create, display, edit, search and remove 
product records. The actual supported operations depend on the program implementation. A database 
can retain records even after the application is closed.

1.4 Overview of the project 
The proposed application uses Java Swing to present windows, labels, fields, buttons and tables. 
Application logic checks the entered values and decides which operation to perform. JDBC provides 
the interface for executing SQL statements, while MySQL stores the information. This separation 
makes the design easier to understand and maintain. 
1.5 Why this is more than a spreadsheet 
A spreadsheet is convenient for small lists, but it depends on manual discipline. It can contain 
duplicate identifiers, invalid quantities and inconsistent price formats. A database-backed application 
can check inputs before saving and use database constraints to protect records.

2. Problem Statement 
2.1 Background 
Small businesses often keep product details in handwritten stock books, spreadsheet files or messages. 
A price change may be updated in one place but missed in another. Without a central record, it is hard 
to know which information is correct. 
2.2 Problem 1: Scattered information 
Separate records lead to duplicated product entries, inconsistent names, old prices and slow searching. 
Staff may spend unnecessary time comparing lists before making decisions. 
2.3 Problem 2: Weak data entry 
A user may accidentally leave a product name empty, enter a negative quantity or type letters in a 
numeric price field. Unchecked values reduce the usefulness of reports and stock records. 
2.4 Problem 3: No persistent storage 
Data stored only in a running program disappears when it closes. Product details should remain 
available after restart and should be retrievable by a stable identifier.

3. Existing Approaches and Their Limitations 
3.1 Manual registers 
Paper records are inexpensive and easy to start, but they are slow to search and difficult to correct 
consistently. Pages may be misplaced or damaged. 
3.2 Spreadsheet-based tracking 
Spreadsheets support sorting and filtering, but copies can become inconsistent. Data validation is often 
incomplete and users may overwrite cells accidentally. 
3.3 Generic billing applications 
Large billing and enterprise systems provide many functions but can be costly or unnecessarily 
complicated for a small product-record exercise. 
3.4 Comparison 
Approach Advantage Limitation 
Paper register Simple Slow search; loss risk 
Spreadsheet Familiar and flexible Duplicate copies and invalid entries 
Large commercial system Rich functions More setup and cost 
Desktop database application Structured local records Requires Java and database setup 
These limitations motivate a lightweight application focused on clear product data entry and reliable 
storage.

5. Proposed Solution 
5.1 Overall idea 
The user enters product details in a Java Swing form. Application logic checks values, selects an 
operation and calls the JDBC data-access layer. MySQL stores or returns the requested records. The 
result appears in the application window. 
Problem Proposed response 
Scattered information One MySQL database 
Incorrect values Input validation 
Temporary records Persistent storage 
Hard-to-maintain code Separate interface and database operations 
5.2 Presentation module (Java Swing) 
The presentation module uses windows, panels, text fields, labels, buttons, message dialogs and tables. 
Its responsibility is to collect user input and display results. SQL statements should not be embedded 
directly inside visual components. 
5.3 Application logic module 
This module receives actions, checks required fields, validates numeric values and decides whether the 
requested operation should continue.

5.4 Data-access module (JDBC) 
JDBC opens connections, sends SQL statements and reads database results. PreparedStatement should 
be used for user-provided values. Connections, statements and result sets should be closed after use. 
5.5 Database module (MySQL) 
MySQL maintains product records in relational tables. A recommended conceptual product table 
includes product_id, product_name, category, price and quantity. These are illustrative fields and 
should be aligned with the actual schema. 
5.6 Validation module 
A product name should not be blank. Price and quantity should be checked for valid numeric types and 
permitted ranges. Duplicate identifiers should be handled through a suitable database constraint. 
5.7 Workflow of a typical operation 
1. Open the application. 
2. Enter or select product information. 
3. Choose a supported action. 
4. Validate the entered values. 
5. Execute a parameterised database operation. 
6. Refresh the displayed records and show a result message.

8. Security and Control 
A product management application should protect stored information and avoid unsafe database 
operations. The following controls are recommended design requirements, not verified implementation 
claims.

8.1 Recommended controls 
• Validate all required input before SQL operations. 
• Use PreparedStatement parameters for values. 
• Keep passwords out of public source files. 
• Use a database account with limited permissions. 
• Close database resources after use. 
• Display clear user messages and keep technical details in logs. 
8.2 Input validation 
Prices and quantities require numeric checks. Names and categories should have appropriate length 
limits. Invalid input should be rejected before it reaches the database. 
8.3 SQL safety 
Parameterised SQL prevents user text from being interpreted as SQL instructions. It is preferred over 
building queries by joining strings. 
8.4 Credential protection 
Database passwords should be stored in protected local configuration or environment variables rather 
than hard-coded into public code.
